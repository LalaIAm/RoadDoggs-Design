# RoadDoggs Design System — Design Document

## Overview

The RoadDoggs Design System is a living component library built on React 19, SCSS (sass-embedded), and Storybook 10. It codifies the brand's visual language — warm earth tones, three-font typographic system, and "Curated Chaos" aesthetic — into a set of reusable, accessible, and well-documented components. Every component is grounded in the SCSS token system defined in `_theme.scss`, follows BEM naming with the `rd-` prefix, and is documented in Storybook under a four-tier sidebar hierarchy: Docs / Atoms / Molecules / Organisms.

The system covers 25 requirements spanning design tokens, 20+ components, Storybook documentation pages, accessibility compliance, and brand voice. This document is the single source of truth for implementation: a developer should be able to build every component from this document alone without referring back to the requirements.

### Key Design Decisions

- **Token-first**: All color, spacing, typography, shadow, radius, and transition values live in `_theme.scss` as SCSS variables and are mirrored as CSS custom properties on `:root`. Component partials access tokens via `@use 'theme' as t` and reference them as `t.$variable-name`.
- **BEM + rd- prefix**: Every block class is prefixed `rd-` (e.g., `rd-button`, `rd-card`). Elements use `__` and modifiers use `--`. No utility classes.
- **One partial per component**: Each component has exactly one SCSS partial under `src/styles/scss/components/`. All partials are imported in `styles.scss` via `@use`.
- **PropTypes only**: No TypeScript. All prop documentation is via `prop-types` and Storybook Autodocs.
- **Accessibility first**: WCAG 2.1 AA minimum. Every interactive component has visible focus rings, correct ARIA roles, and keyboard support.
- **Brand voice throughout**: Story copy, prop descriptions, and MDX pages use approved RoadDoggs terminology. No lorem ipsum, no SaaS language.

### `@use 'theme'` Pattern in Component Partials

Every component partial uses the following import pattern. The `as t` alias keeps references short and unambiguous:

```scss
// src/styles/scss/components/_button.scss
@use "../theme" as t;

.rd-button {
  font-family: t.$font-body;
  padding: t.$space-3 t.$space-6;
  border-radius: t.$radius-pill;
  transition:
    transform t.$transition-base,
    box-shadow t.$transition-base;

  &--primary {
    background: t.$burnt-orange;
    color: t.$dust-white;
  }
}
```

The existing `_accordion.scss` uses `@use '../theme'` (without alias). New partials use `@use '../theme' as t` for consistency. The existing `_alert.scss` hardcodes color values and should be refactored to use `@use '../theme' as t` during the token expansion task.

| -------- | -------------------------------------- | ------- | ------------------------------------ |

**JSX Structure**

```jsx
<section className="rd-accordion">
  <p className="rd-accordion__eyebrow">{title}</p>
  <h2 className="rd-accordion__heading">{subtitle}</h2>
  <div className="rd-accordion__list">
    {items.map((item, index) => (
      <article
        key={item.title}
        className={`rd-accordion__item${openIndex === index ? " rd-accordion__item--open" : ""}`}
      >
        <button
          className="rd-accordion__trigger"
          onClick={() => toggleItem(index)}
          aria-expanded={openIndex === index}
        >
          <span>{item.title}</span>
          <span className="rd-accordion__icon" aria-hidden="true">
            {openIndex === index ? "−" : "+"}
          </span>
        </button>
        <div className="rd-accordion__panel">
          <p>{item.content}</p>
        </div>
      </article>
    ))}
  </div>
</section>
```

#### Button

**Props Interface**

| Prop         | Type                                                        | Default     | Description                                    |
| ------------ | ----------------------------------------------------------- | ----------- | ---------------------------------------------- |
| variant      | `'primary' \| 'dark' \| 'secondary' \| 'ghost' \| 'danger'` | `'primary'` | Visual style                                   |
| size         | `'sm' \| 'md' \| 'lg'`                                      | `'md'`      | Button size                                    |
| disabled     | boolean                                                     | `false`     | Disables interaction and applies muted styling |
| loading      | boolean                                                     | `false`     | Replaces label with spinner, sets `aria-busy`  |
| icon         | node                                                        | —           | Optional SVG icon element                      |
| iconPosition | `'left' \| 'right'`                                         | `'left'`    | Icon placement relative to label               |
| onClick      | function                                                    | —           | Click handler                                  |
| children     | node                                                        | —           | Button label text                              |

**JSX Structure**

```jsx
<button
  className={`rd-button rd-button--${variant} rd-button--${size}${disabled ? " rd-button--disabled" : ""}${loading ? " rd-button--loading" : ""}`}
  disabled={disabled || loading}
  aria-busy={loading || undefined}
  onClick={onClick}
>
  {loading ? (
    <span className="rd-button__spinner" aria-hidden="true" />
  ) : (
    <>
      {icon && iconPosition === "left" && (
        <span
          className="rd-button__icon rd-button__icon--left"
          aria-hidden="true"
        >
          {icon}
        </span>
      )}
      <span className="rd-button__label">{children}</span>
      {icon && iconPosition === "right" && (
        <span
          className="rd-button__icon rd-button__icon--right"
          aria-hidden="true"
        >
          {icon}
        </span>
      )}
    </>
  )}
</button>
```

- Focus ring uses `outline` on `:focus-visible` only — not `:focus` — to avoid mouse-click outlines

## Correctness Properties

These are the formal properties the design system must uphold. They are expressed as testable invariants and serve as the basis for property-based and interaction tests.

### Property 1: Token Completeness

**Validates: Requirements 1.1, 1.2, 1.3, 1.6, 14.4, 14.5**

Every component SCSS partial that references a `t.$variable` must have a corresponding variable defined in `_theme.scss`. No partial may reference an undefined token.

### Property 2: CSS Custom Property Parity

**Validates: Requirements 1.4**

Every SCSS variable defined in `_theme.scss` must have a corresponding `--rd-*` CSS custom property emitted on `:root`. The set of SCSS variables and CSS custom properties must be in 1:1 correspondence.

### Property 3: No Hardcoded Values

**Validates: Requirements 1.5, 14.4**

No component SCSS partial may contain hardcoded color hex values, pixel spacing values, or font-family strings. All such values must reference `t.$variable-name`.

### Property 4: Disabled Buttons Never Fire

**Validates: Requirements 2.6**

When a Button has `disabled={true}` or `loading={true}`, the `onClick` handler must never be called regardless of click or keyboard activation.

### Property 5: StepperInput Bounds Enforcement

**Validates: Requirements 18.3, 18.4, 18.5, 18.6**

When `value === min`, the decrement button must be disabled and `onChange` must not be called with a value below `min`. When `value === max`, the increment button must be disabled and `onChange` must not be called with a value above `max`.

### Property 6: Modal Focus Containment

**Validates: Requirements 7.3**

While a Modal is open (`isOpen={true}`), Tab and Shift+Tab must cycle focus only among focusable elements within the dialog panel. No focus must escape to the document behind the overlay.

### Property 7: Modal Closes on Escape and Backdrop Click

**Validates: Requirements 7.4, 7.5**

Pressing Escape or clicking the overlay backdrop while a Modal is open must call `onClose` exactly once. Clicking inside the dialog panel must not call `onClose`.

### Property 8: Navigation Drawer Focus Return

**Validates: Requirements 9.4**

When the mobile nav drawer is closed (via Escape or a close action), focus must return to the hamburger button that opened it.

### Property 9: Toast Auto-Dismiss Timing

**Validates: Requirements 8.3, 8.4**

When a Toast has a `duration` prop set to a positive integer N, the `onDismiss` callback must be called after at least N milliseconds and no more than N + 500 milliseconds (allowing for animation).

### Property 10: SelectionCard Keyboard Activation

**Validates: Requirements 17.4, 17.5**

Pressing Enter or Space on a focused SelectionCard must call `onSelect` with the card's `id`. Mouse click must also call `onSelect`.

### Property 11: TabBar Arrow Navigation

**Validates: Requirements 21.7**

Pressing ArrowRight on a focused tab must move focus to the next tab (wrapping from last to first). Pressing ArrowLeft must move focus to the previous tab (wrapping from first to last).

### Property 12: Chip Toggle Invariant

**Validates: Requirements 19.5**

After calling `onToggle`, the `active` prop passed to the next render must be the logical inverse of the previous `active` value.

### Property 13: Focus Ring Visibility

**Validates: Requirements 2.7, 13.3, 15.5, 17.5**

Every interactive component (Button, Input, Checkbox, Chip, SelectionCard, TabBar tab, Card interactive, Navigation links, Modal close) must render a visible focus ring when focused via keyboard (`:focus-visible`). The focus ring must have a minimum 3:1 contrast ratio against its background.

### Property 14: Color-Independent Meaning

**Validates: Requirements 13.5**

Every component that uses color to convey state (Alert variant, Badge variant, Toast variant, ProgressStepper step state, SelectionCard selected state) must also convey that state through text, icons, or ARIA attributes — not color alone.

### Property 15: Form Label Association

**Validates: Requirements 4.1, 13.6, 15.1**

Every Input and Checkbox must have a `<label>` element whose `htmlFor` matches the input's `id`. The association must be programmatic, not just visual proximity.

### Property 16: ARIA Role Correctness

**Validates: Requirements 7.6, 16.7, 17.6, 21.6**

SelectionCard must have `role="radio"` and `aria-checked`. TabBar container must have `role="tablist"` and each tab must have `role="tab"` with `aria-selected`. Modal must have `role="dialog"` and `aria-modal="true"`. ProgressStepper active node must have `aria-current="step"`.

### Property 17: No Banned Terminology

**Validates: Requirements 25.2**

No story label, prop description, example copy, or MDX page content may contain the words: Itinerary, Optimize, Algorithm, Generate, User (as a noun for a person), Platform, Solution, or Leverage.

### Property 18: Approved Terminology Usage

**Validates: Requirements 25.1, 25.3, 25.4**

All story copy and MDX documentation must use the approved substitutions: Route (not Trip), Game Plan (not Itinerary), Spots (not Stops), Finds (not Points of Interest), Co-Pilot (not AI Assistant), Tweak (not Edit/Modify).

## Error Handling

### Icon — Unknown Symbol Name

If the `name` prop passed to Icon does not match any symbol ID in `public/icons.svg`, the `<use>` element renders nothing. The component does not throw. To prevent silent invisible icons in production, the Icon story grid serves as a visual regression check — any missing symbol will appear as an empty cell.

**Mitigation**: Maintain a `VALID_ICON_NAMES` constant (array of known symbol IDs) in `Icon.jsx` and add a PropTypes `oneOf(VALID_ICON_NAMES)` validator. Storybook's Controls panel will surface invalid values during development.

### Avatar — Image Load Failure

If the `src` image fails to load (404, network error), the `<img>` element's `onError` handler sets a local `imgError` state flag, which causes the component to render the initials fallback instead. The `alt` attribute is always set to `name` regardless of which branch renders.

### Modal — No Focusable Children

If a Modal's dialog panel contains no focusable elements (e.g., body-only content with no buttons), the focus management logic falls back to focusing the dialog panel element itself (`tabIndex={-1}` on `.rd-modal`). This ensures focus is always moved into the dialog on open.

### Toast — Missing onDismiss

If `duration` is set but `onDismiss` is not provided, the Toast auto-dismiss timer fires but has no callback to call. The component handles this gracefully by checking `if (onDismiss) onDismiss()` before calling the prop. The Toast will still animate out and unmount if the parent manages visibility via state.

### StepperInput — Out-of-Range Initial Value

If `value` is initialized below `min` or above `max`, the component renders correctly but both buttons may be in an unexpected state. The component does not clamp the value — that is the responsibility of the parent. A PropTypes warning is emitted in development if `value < min` or `value > max`.

### SCSS Compilation — Missing Token Reference

If a component partial references a token that does not exist in `_theme.scss`, the SCSS compiler will throw a build error (`Undefined variable`). This is intentional — it surfaces missing tokens at build time rather than silently producing broken styles. The fix is always to add the missing token to `_theme.scss` before using it in a partial (per Requirement 14, AC5).

### Storybook — MDX Import Errors

If an MDX page references a component or asset that does not exist, Storybook will fail to compile that page and show an error in the sidebar. Each MDX page should be tested in isolation after creation by running `storybook dev` and verifying the page renders without errors.

## Testing Strategy

### Overview

Testing for the RoadDoggs Design System operates at three levels: static analysis (PropTypes + SCSS compilation), Storybook interaction tests (component behavior), and accessibility audits (a11y addon + manual review). Property-based testing (PBT) is used for components with bounded numeric inputs and toggle state.

### Level 1 — Static Analysis

**SCSS compilation**: Running `sass src/styles/scss/styles.scss` must complete without errors. Any undefined token reference or import failure is a build-time error. This is the first gate in any CI pipeline.

**PropTypes validation**: All components define PropTypes. Running Storybook in development mode surfaces PropTypes warnings in the browser console. Stories are written to exercise all prop combinations, ensuring warnings surface during story development.

### Level 2 — Storybook Interaction Tests

Storybook's `@storybook/addon-vitest` integration runs interaction tests defined in story files using the `play` function. Each interactive component has at least one interaction test covering its primary behavioral property.

**Button**

```js
// Verifies P4 — disabled buttons never fire
export const DisabledNoClick = {
  args: { disabled: true, children: "Next Step →", onClick: fn() },
  play: async ({ args, canvasElement }) => {
    const button = within(canvasElement).getByRole("button");
    await userEvent.click(button);
    expect(args.onClick).not.toHaveBeenCalled();
  },
};
```

**StepperInput**

```js
// Verifies P5 — bounds enforcement
export const DecrementAtMin = {
  args: { label: "Adults", value: 0, min: 0, max: 10, onChange: fn() },
  play: async ({ args, canvasElement }) => {
    const decBtn = within(canvasElement).getByLabelText("Decrease Adults");
    expect(decBtn).toBeDisabled();
    await userEvent.click(decBtn);
    expect(args.onChange).not.toHaveBeenCalled();
  },
};
```

**Modal**

export const ClosesOnEscape = {

### Level 3 — Accessibility Audits

**Automated (a11y addon)**: The `@storybook/addon-a11y` addon runs axe-core checks on every story. The `a11y: { test: "todo" }` setting in `preview.js` means violations are surfaced as warnings during development. Before a component is considered complete, all axe violations must be resolved.

**Manual keyboard testing**: Each interactive component must be manually tested for keyboard operability:

- Tab to reach the component
- Activate with Enter/Space
- Navigate with arrow keys where applicable (TabBar, Navigation links)
- Verify focus ring is visible at each step
- Verify screen reader announces state changes (checked, selected, expanded, current)

**Color contrast verification**: The token pairs used for text-on-background must meet WCAG AA (4.5:1 for normal text, 3:1 for large text and UI components). Key pairs to verify:

- `$road-black` on `$dust-white`: ~14:1 ✓
- `$dust-white` on `$burnt-orange`: ~3.2:1 (large/bold text only — verify per usage)
- `$dust-white` on `$road-black`: ~14:1 ✓
- `$muted-rust` on `$dust-white`: ~4.6:1 ✓
- `$asphalt-gray` on `white`: ~10:1 ✓

Note: Full WCAG validation requires manual testing with assistive technologies and expert accessibility review. Automated axe checks catch common violations but do not guarantee full compliance.

### Property-Based Testing

For components with numeric inputs (StepperInput) and toggle state (Chip, SelectionCard, Checkbox), property-based tests use fast-check to generate arbitrary valid inputs and verify invariants hold across the full input space.

**StepperInput — value never escapes bounds**

```js
import fc from "fast-check";

test("StepperInput value stays within [min, max]", () => {
  fc.assert(
    fc.property(
      fc.integer({ min: 0, max: 5 }), // min
      fc.integer({ min: 6, max: 20 }), // max
      fc.integer({ min: 0, max: 20 }), // initial value
      (min, max, initial) => {
        const value = Math.min(Math.max(initial, min), max);
        // Simulate increment
        const afterIncrement = value < max ? value + 1 : value;
        expect(afterIncrement).toBeGreaterThanOrEqual(min);
        expect(afterIncrement).toBeLessThanOrEqual(max);
        // Simulate decrement
        const afterDecrement = value > min ? value - 1 : value;
        expect(afterDecrement).toBeGreaterThanOrEqual(min);
        expect(afterDecrement).toBeLessThanOrEqual(max);
      },
    ),
  );
});
```

**Chip — toggle is always the logical inverse**

```js
test("Chip onToggle always inverts active state", () => {
  fc.assert(
    fc.property(fc.boolean(), (active) => {
      let result;
      const onToggle = (val) => {
        result = val;
      };
      // Simulate click
      onToggle(!active);
      expect(result).toBe(!active);
    }),
  );
});
```
